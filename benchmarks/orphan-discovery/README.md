# Orphan discovery benchmark: how to read it

`report.md`, `results.json` and `plans.json` are generated by `scripts/bench/orphan-discovery.mjs`
and are the original measurements; they are not edited by hand. This file separates what they
measured from what is inferred.

Index variants: **A** = partial `document_versions (updated_at, id) where status in ('uploaded','queued')`;
**B** = `outbox (workspace_id, version_id) include (dispatched_at)`; **B-no-include** = the same
index without `INCLUDE`.

## Measured

All ranges below are the min-max of per-scenario execution times (four cursor depths: page 1, 50%,
90%, 99%) in `results.json`, 500-row pages, 200k waiting versions. "Pre-VACUUM" is the freshly
loaded state (visibility map empty); "post-VACUUM" follows a `VACUUM` of both tables. Timings are
medians of three runs, except runs over 5 s, which were measured **once** (no median).

| Variant | Pre-VACUUM privileged | Pre-VACUUM worker | Post-VACUUM privileged | Post-VACUUM worker |
|---|---|---|---|---|
| baseline | 17.0-21.8 s (1 run) | 4/4 hit the 15 s timeout | 15.2-18.2 s (1 run) | 3/4 timed out; page 1, 50% and 90% timed out, 99% finished in 14.6 s (1 run) |
| A | 16.2-23.3 s (1 run) | 4/4 timeout | 14.7-17.6 s (1 run) | 13.3-14.9 s (1 run) |
| B | 21.9-45.3 ms | 22.9-117 ms | 21.4-49.1 ms | 22.3-42.2 ms |
| A+B | 3.0-3.9 ms | 2.5-3.4 ms | 2.1-2.8 ms | 2.0-2.6 ms |
| B-no-include | 24.1-46.0 ms | 21.0-57.7 ms | 25.1-42.3 ms | 20.6-43.6 ms |
| A+B-no-include | 2.5-5.7 ms | 3.4-6.5 ms | 2.2-3.1 ms | 2.2-2.3 ms |

- A alone does not help: still 13-23 s, or timeout for the worker role pre-VACUUM. B is the fix.
- Index sizes: B 40.6 MB, B-no-include 17.8 MB, A 8.1 MB.
- `lockOrphan`'s second statement: 25.5-28.1 ms without B (baseline, A, A-include); 0.02-0.05 ms with
  any B variant, in both phases and roles.
- Heap fetches with B: 2120-2132 pre-VACUUM (stale visibility map), 0 post-VACUUM. Post-VACUUM
  is the steady state with autovacuum on; the benchmark ran with autovacuum off.

## Recommendation (pending)

Measured recommendation, not yet applied:

- **Index A**: `document_versions (updated_at, id) WHERE status IN ('uploaded', 'queued')`.
- **Index B**: `outbox (workspace_id, version_id)`, **without** `INCLUDE`.

B-no-include read latency matched B at less than half the size. We do not claim `INCLUDE
(dispatched_at)` newly prevents HOT updates: the existing partial indexes already reference
`dispatched_at`. These remain recommendations until the clustered-backlog scenario below has run and
migration 0013 is separately approved.

## Not measured

- Write throughput or index-maintenance overhead of any variant.
- Concurrent writes while discovery runs.
- Cold-cache behaviour (all runs are warm; reads came from shared buffers).
- Anything other than one dataset, one PostgreSQL build and one tmpfs-backed container.

## Limits of the A+B result

The 2-4 ms figure comes from a synthetic dataset where ineligible rows (exhausted attempts, deleted
documents, live outbox, cooldown) are spread **uniformly** through `updated_at` order. It does not
establish worst-case latency for a clustered backlog.

## Remaining performance risk

Discovery filters on `status` and `attempt < 3` on `document_versions` before the lateral outbox
lookup, so exhausted-attempt rows never trigger that lookup; they only cost version index/heap
scanning. Other ineligible rows do reach it:

- Deleted-document versions stay discoverable (the worker cannot see `documents`), so they occupy
  page slots and cause the separately tracked starvation problem; `lockOrphan` rejects them later.
- Live-outbox and cooldown candidates pass the version filters, run the lateral lookup, and are
  rejected only afterwards.

A concentrated group of such candidates in one region of `(updated_at, id)` order raises the work
needed to fill a page whenever the cursor crosses that region. Where fresh uploads sit in that order
depends on their timestamps, so the position of a cluster is not fixed.

Before finalizing migration 0013, add a separate scenario (not implemented or run here) with
concentrated live-outbox and cooldown candidates at different cursor positions (start, middle, end).

## Hygiene and what to commit

`results.json`, `plans.json` and `report.md` were checked for credentials, connection strings,
usernames and absolute paths: none present. They contain only `127.0.0.1`, an ephemeral port, the
pinned image digest, Postgres settings and plan data. Recommended to commit for reproducibility:
`scripts/bench/*`, this README, `report.md` (human-readable) and `results.json`. `plans.json`
(694 KB of full EXPLAIN output) is optional; commit it only if reviewers need the raw plans.
